# Функциональное техническое задание (BRD / FRD)

**Документ:** `docs/requirements/identity-audit-compliance-service-functional-spec.md`
**Статус:** Approved for Development
**Сервис:** identity-audit-compliance-service (Поддомен: Warehouse Cross-Docking & B2B EDI)

## 1. Введение и Назначение Сервиса

### 1.1 Бизнес-контекст
В международной логистической платформе работают тысячи пользователей разных ролей и организаций: внутренние диспетчеры, кладовщики, внешние водители, сторонние перевозчики, таможенные агенты и клиенты. `identity-audit-compliance-service` обеспечивает единую точку управления идентичностью (IAM), строгую политику доступа на основе контекста (ABAC) и ведёт защищенный журнал аудита всех юридически значимых действий.

### 1.2 Проблемы, которые решает сервис
*   **Уход от жестких ролевых моделей (RBAC limits):** В логистике ролей недостаточно («Диспетчер должен видеть только те грузы, которые физически находятся в его домашнем регионе»).
*   **Защита коммерческой тайны контрагентов:** Сторонний перевозчик не должен видеть стоимость доставки и грузы других перевозчиков, даже если у них одинаковые роли в системе.
*   **Юридический аудит и разбор инцидентов:** Невозможность незаметно удалить или изменить историю операций, статусы грузов или финансовые акты в системе при расследованиях.

## 2. Доменная модель и Сущности (Domain Entities)

Сервис оперирует сущностями безопасности и аудиторского следа:

```text
 ┌──────────────────────┐       1..N      ┌──────────────────────┐
 │     UserIdentity     ├────────────────►│     AccessPolicy     │
 └──────────────────────┘                 └──────────────────────┘
                                                     ▲
 ┌──────────────────────┐                            │
 │     AuditEvent       ├────────────────────────────┘
 └──────────────────────┘
```

*   **UserIdentity (Идентичность пользователя):** Единый профиль субъекта (из Keycloak/OAuth2). Содержит статичные роли и динамические контекстные атрибуты (`organization_id`, `assigned_region_code`, `allowed_hubs_list`, `clearance_level`).
*   **AccessPolicy (Политика доступа ABAC):** Правило разрешения или запрета действия на основе сравнения атрибутов субъекта и целевого объекта. Пример: `Subject.OrganizationID == Resource.CarrierID`.
*   **AuditEvent (Аудиторская запись):** Неизменяемая запись о совершенном действии. Атрибуты: `event_id`, `timestamp`, `actor_id`, `actor_role`, `action_type` (CREATE, READ, UPDATE, DELETE, EXECUTE), `resource_type`, `resource_id`, `ip_address`, `before_state_json`, `after_state_json`.

## 3. Бизнес-логика и Жизненный Цикл

### 3.1 Принятие решения о доступе (ABAC Decision Flow)

```text
 [Запрос на действие] ──► [PEP (Gateway/Service)] ──► [PDP (ABAC Engine)] ──► [Проверка атрибутов]
                                                             │
                                     ┌───────────────────────┴───────────────────────┐
                                     ▼                                               ▼
                              [PERMIT (Разрешено)]                            [DENY (403 Forbidden)]
                                     │                                               │
                                     └───────────────────────┬───────────────────────┘
                                                             ▼
                                                 [Фиксация в Audit Trail]
```

### 3.2 Основные бизнес-сценарии (Use Cases)

**UC-1: Динамическая проверка прав доступа (Attribute-Based Evaluation)**
1.  Пользователь пытается выполнить действие (например, изменить маршрут заказа #12345).
2.  Микросервис или API Gateway обращается к ABAC-движку сервиса (или использует локальный кеш политик), передавая контекст пользователя и параметры ресурса.
3.  ABAC-движок проверяет правило: `У пользователя есть роль DISPATCHER AND User.region == Order.origin_region`.
4.  Возвращается решение PERMIT или DENY.

**UC-2: Гарантированная запись аудиторского следа (Immutable Audit Logging)**
1.  Любое критическое изменение данных в любом из 10 микросервисов (изменение статуса, цен, доступов) генерирует доменное событие аудита.
2.  Сервис принимает события и записывает их в специальную колоночную БД (ClickHouse) в формате Append-Only (запрет операций UPDATE и DELETE).
3.  Запись подписывается хэш-цепочкой (Cryptographic Audit Hash) для предотвращения ручной подмены логов администраторами баз данных.

**UC-3: Формирование отчетов для внешних аудиторов (Compliance Reporting)**
Выгрузка полной неизменяемой истории конкретного рейса со всеми изменениями, авторизациями и отказами в доступе за любой период времени по запросу службы безопасности или международных регуляторов.

## 4. Функциональные требования (Functional Requirements)

*   **FR-1:** Сервис ДОЛЖЕН интегрироваться с Keycloak как с единым провайдером идентичности (Identity Provider / OpenID Connect).
*   **FR-2:** Сервис ДОЛЖЕН предоставлять высокоскоростной PDP-эндпоинт (Policy Decision Point) для проверки ABAC-правил.
*   **FR-3:** Сервис ДОЛЖЕН вести неизменяемый (Immutable) журнал аудиторских событий всех изменений данных платформы.
*   **FR-4:** Сервис ДОЛЖЕН обогащать токены JWT необходимыми контекстными атрибутами пользователей при авторизации.
*   **FR-5:** Сервис ДОЛЖЕН предоставлять REST API для поиска и фильтрации аудиторских логов для офицеров безопасности.
*   **FR-6:** Сервис ДОЛЖЕН блокировать любые попытки удаления или модификации ранее записанных аудиторских логов.

## 5. Требования к качеству и SLA (Non-Functional Requirements)

*   **NFR-1 (Availability):** Высокая доступность 99.99% (выход из строя сервиса аудита не должен полностью парализовать чтение данных, но должен переводить запись в безопасный режим).
*   **NFR-2 (ABAC Performance):** Время принятия решения по проверке атрибутов доступа — не более 5 ms (p99).
*   **NFR-3 (Audit Throughput):** Способность принимать и сохранять до 20,000 аудиторских событий в секунду без потери производительности.
